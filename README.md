# Tree Agent

一個 Windows 桌面 GUI，把 Codex CLI 包起來，補上 Codex 目前缺的**樹狀專案結構**。

Codex 的專案列表是平面的：每個專案只是一個資料夾，對話全部混在一起。Tree Agent 改成：

- **專案可以無限層嵌套** — 專案底下可以有子專案，子專案底下還能再有子專案。
- **每個對話屬於一個專案，並擁有自己的 Codex thread** — 切換對話不會混到別的上下文。
- **設定沿樹繼承** — 工作目錄 / 模型 / 沙箱模式設在專案上，子專案與對話自動繼承，只在需要時覆寫。
- **多個對話可同時執行** — 各自獨立的 `codex exec` 行程，樹上以 ⏳ 標示。

```
📁 客戶A
   📁 認證中心            ← cwd = E:\repo\sso, sandbox = read-only
      💬 排查 401 錯誤     ← 自己的 thread
      💬 redirect_uri 調查 ← 自己的 thread
   📁 檔案系統
      📁 上傳模組         ← 覆寫 cwd，其餘繼承「客戶A」
         💬 效能調校
📁 內部工具
   💬 每日備份腳本
```

## 需求

- Windows 10 / 11
- Python 3.10+（用內建的 Tkinter，**不需要安裝任何套件**）
- Codex CLI 已安裝並在 PATH 中：`npm install -g @openai/codex`，且已 `codex login`
  （對著 **0.149.0** 驗證過；0.147.0 也可用 — 用到的 CLI 介面兩版相同）

## 執行

```bash
python -m tree_agent
```

或直接雙擊 `run.cmd`（有 `pythonw` 時不會留下黑色主控台視窗）。

想用另一個獨立的工作區：

```bash
python -m tree_agent --home D:\my-other-workspace
```

## 操作

| 動作 | 方式 |
| --- | --- |
| 新增對話 | 「＋對話」一下就好 — **不問名字**，直接建好並切過去，游標落在輸入框；送出第一則訊息後會**自動命名** |
| 新增最上層專案 / 子專案 | 左上按鈕、`檔案` 選單，或樹上右鍵（專案**會**問名字） |
| 送出訊息 | `Enter`，或按「送出」；執行中送出的訊息會排入佇列 |
| 換行 | `Shift+Enter` |
| 重新命名 | `F2` |
| 刪除 | `Del` — 刪完會選到下一個同層項目（沒有就上一個，再沒有就上層專案），樹的展開狀態保持原樣 |
| 搬移專案或對話 | 在樹上拖曳。放到專案上＝移進去；放到對話上＝插到它前面；放到空白處＝變成最上層專案 |
| 修改專案設定 | 點選專案，右側就是設定表單（欄位留空 = 繼承上層） |
| 選擇對話 Agent | 在對話標題列選擇 Codex CLI 或 Claude Code；新對話預設為 Codex CLI |
| 設定 Agent 執行檔 | `檔案` 選單 →「Agent 設定」；會自動偵測系統 PATH，也可指定執行檔位置 |
| 設定專案提示詞 | 專案設定表單最下方的「提示詞」（見下方「專案提示詞」） |
| 收緊某個專案的權限 | 預設已是最高權限；要限制就把該專案的沙箱模式改成 `read-only` 或 `workspace-write`（見下方「權限」） |
| 匯出／匯入 | 樹上**右鍵**，或 `檔案` 選單（見下方「匯出與匯入」） |
| 搜尋專案／對話／內容 | 樹上方的搜尋框，或 `Ctrl+F` |
| 跳到對話某一段 | 點左側「大綱」裡的項目 |
| 調整四個區塊的寬度 | 直接拖曳三條分隔線；寬度會記住 |
| 開關左右兩個面板 | `檢視` 選單：顯示對話大綱（左）／顯示資訊面板（右） |
| 切換深色模式 | `檢視` 選單：深色模式／淺色模式；選擇會記住 |
| 讓逐字稿填滿它的區塊 | `檢視` 選單取消「限制逐字稿行寬」 |
| 跳到對話最新處 | 往上翻時右下角會出現「↓ 跳到最新」 |
| 展開／收合某個工具輸出 | 點那一行的 `▸` 摘要 |
| 改變工具輸出的顯示方式 | `檢視` 選單：收合成一行（預設）／完整顯示／完全隱藏 |
| 複製對話中的文字 | 直接拖選，`Ctrl+C`（或 `Ctrl+Insert`）；`Ctrl+A` 全選；右鍵有選單 |
| 從這裡分岔出新對話 | 對話上右鍵 →「從這裡分岔出新對話」，或標題列的「分岔」鈕（見下方「分岔對話」） |
| 附加圖片給 Codex | 輸入框 **右鍵 →「貼上圖片」**、`Ctrl+V`，或「附加圖片」選檔（見下方「圖片」） |
| 審查未提交的變更 | 專案上右鍵 →「審查未提交的變更」 |
| 重設對話 | 右鍵 →「重設對話」，清空內容並在下次送出時開一個新的 Codex thread |

新增對話刻意不問名字：對話是靠內容認的，還沒開始問就要先命名純粹是阻礙。先給一個 `新對話` 的暫名，**送出第一則訊息時自動改成有意義的標題**（見下方「對話自動命名」），`F2` 隨時可以自己改。專案則**保留**命名對話框 — 專案是你會長期共存的容器，還帶著工作目錄／模型／沙箱設定，先取個名字是值得的。

輸入框裡沒送出的文字是**跟著對話走**的：切到別的對話再切回來，草稿還在原處，不會跑到別人身上。（草稿只存在記憶體中，關掉程式就沒了。）

你送出的訊息靠右對齊、Codex 的回覆靠左，一眼分得出誰在說話。

逐字稿是唯讀的，但文字可以自由選取複製。`Ctrl+Enter` 在逐字稿上也能送出，不必先點回輸入框。

## 樹的展開狀態

哪些專案是展開的會記在 `workspace.json` 的 `expanded` 欄位，關掉再開會還原。

這裡有個 Tk 的陷阱值得記：`<<TreeviewOpen>>` / `<<TreeviewClose>>` **不帶是哪一個項目**，而點擊展開箭頭**也不會移動焦點**。原本用 `tree.focus()` 去判斷是誰被展開／收合，結果會把「被點的節點」的狀態寫到「當時有焦點的節點」上 —— 一個工作階段下來就把整棵樹的旗標寫得亂七八糟。現在改成直接掃過所有可見的專案、從 widget 讀回真實狀態，跟事件是誰觸發的無關。

搜尋過濾中會強制把整棵樹展開，那不是真實狀態，所以過濾期間不寫入。

## 閱讀體驗

幾個為了長對話而做的設計，都是繞過 Tk Text 的限制：

**行寬有上限。** Tk 的 Text **沒有**最大寬度選項，所以是把容器加上左右留白、把內容夾在中間（`MAX_CONTENT_PX = 980`）。不限制的話，最大化視窗一行放得下約 237 個英文字元，眼睛要橫掃很遠 — 舒適閱讀遠低於這個數字。

**串流不會把你拽回底部。** `append()` 會在插入前先問 widget「最後一行現在看得到嗎」（`dlineinfo("end-1c")`）；看不到就不自動捲動，並在右下角顯示「↓ 跳到最新」。往上翻讀歷史時，turn 還在跑也不會被打擾。

用 `dlineinfo` 而不是 `yview()` 的比例值：重新排版之後 `yview()[1]` 不保證回到 1.0，任何門檻值都會變成「明明在底部卻跳出按鈕」或「鬆到沒有意義」。問 widget 那一行在不在畫面上是精確的。

**訊息之間有分隔線，但沒有氣泡。** Tk 會把 tag 的背景色**塗滿整行**，不是只塗文字範圍 — 所以「靠右的氣泡」實際上會變成一條橫貫全寬的色帶（實測：文字 bbox 在 x=849，色帶卻是 0→900）。改成靠右對齊＋藍色標籤區分，訊息之間用一條 3px 的細線分隔（作法是一個只有空白字元、1pt 字級、有底色的行）。

**執行中會顯示進度。** 標題列顯示 `⏳ 執行中 12s · 執行指令`，秒數每半秒更新，階段跟著事件流走（啟動中 → 思考中 → 執行指令 → 回覆中）。turn 常跑十幾秒到一分鐘，不用皮定等。

## 左右兩側面板

行寬上限（980px）在寬螢幕上會留下左右兩塊留白，那兩塊各放一個可收合的面板：

**左：對話大綱。** 列出你的提問與 Codex 的 Markdown 標題，點一下就把逐字稿捲到那一段。內容是**從逐字稿已有的 tag 反查**出來的（`role_user`、`md_h1..3` 的 tag 範圍），不需要在渲染流程裡另外埋位置資訊。

**右：資訊面板。** 把原本擠在標題列一行的 `cwd / 模型 / 沙箱 / thread / 用量` 攤開來各佔一行（長路徑不再被截斷），另外列出這個對話的附件縮圖（可點開）與 Codex 動過的檔案（來自 `file_change` 事件）。

兩個面板都能在 `檢視` 選單關掉，選擇記在工作區裡。**視窗太窄時會自動收起**：先收右邊的資訊面板，再收左邊的大綱 —— 因為大綱是導覽工具，比較該留。

### 寬度可以拖

四個區塊之間的三條分隔線都能拖動，寬度存在工作區裡、下次開啟還原：

```
專案樹 │ 大綱 │ 逐字稿 │ 資訊
      ↑      ↑        ↑
      都可以拖
```

實作上是把原本固定寬度的 grid 換成 `ttk.PanedWindow`。兩個 Tk 細節值得記：

- **`sashpos` 在 `add` 之後馬上設定不會生效** —— 那時候 pane 還沒有 geometry。改成靠每個軌道自己的 `width` 請求值，這是 PanedWindow 加入 pane 時真正會參考的東西。
- 存的是**寬度**而不是 sash 位置。顯示／隱藏面板會讓 pane 數量改變，sash 的索引與座標跟著變，寬度才是穩定的量。

行寬上限（`MAX_CONTENT_PX = 980`）現在只管**逐字稿區塊裡的文字**，跟 pane 大小分開：把逐字稿拖寬只會增加它兩側的留白，文字仍維持可讀寬度。如果你想讓文字填滿你拖出來的空間，`檢視` 選單取消「限制逐字稿行寬」。

留白是用 Text 自己的 `-padx`（widget 內縮），不是在 widget 外面加 padding。這一點很重要：外部 padding 會讓**你看到的白色區邊界和真正的 sash 相差 180px** —— 你會去拖你看得到的那條邊，那裡什麼都沒有，於是「只有資訊面板左邊那條能拖」。改成內縮之後，白色區的邊界就落在 sash 上（實測相差 6px），右邊則是捲軸緊貼 sash（相差 1px）。

## 搜尋

樹上方的搜尋框（或 `Ctrl+F`）會即時過濾，比對三個地方：專案名稱、對話名稱、**逐字稿內容**。

- 命中的節點會連同它的上層一起顯示，路徑不會斷掉
- 命中的**專案**會連同它底下的全部內容一起顯示（搜專案名就是想看裡面）
- 過濾時整棵樹自動展開，不用一層層點開
- 不分大小寫；狀態列顯示命中幾個項目
- 打字有 250ms 的防抖，因為要掃逐字稿內容
- `Esc` 或 ✕ 清除

## 分岔對話

同一段脈絡想試兩條不同路線時，不必重新解釋一遍背景 — 從既有對話「分岔」出一個新的：

```
📁 認證中心
   💬 排查 401 錯誤            ← 已經釐清了背景
   💬 排查 401 錯誤 (分岔)     ← 繼承上面的全部上下文，之後各走各的
   💬 排查 401 錯誤 (分岔 2)   ← 再開一條
```

底層用 `codex exec fork <thread_id>`。實測語意（codex 0.149）：

| thread | 記得什麼 |
| --- | --- |
| 來源 | 分岔前的內容 |
| 分岔 | 分岔前的內容 **＋** 分岔後它自己新增的 |
| 來源（分岔後） | **不受影響** — 分岔那邊加的東西它看不到 |

也就是 copy-on-write 分支。幾個實作細節：

- 分岔出來的對話會**複製逐字稿**，所以你看得到 Codex 已經知道什麼，並在結尾標一行「以上內容分岔自「X」」標示分界。
- 真正的新 thread 是**第一次送出訊息時**才建立的（`codex exec fork` 會回一個新的 `thread_id`）。在那之前樹上顯示 🌿，送出後變成 💬。
- 之後每一回合都走 `resume` 自己的 thread，不會重複 fork。
- 還沒送過訊息的對話無法分岔（沒有 thread 可分），「分岔」鈕會是灰的。
- 分岔的名稱不會疊加後綴：從「X (分岔)」再分岔會得到「X (分岔 2)」，不是「X (分岔) (分岔)」。

## 工具輸出

Codex 執行一個 `git status` 或列檔案，動輒吐出上百行，把它正要講的結論擠到看不見。所以**指令執行預設收合成一行**：

```
▸ $ pwsh -Command 'rg --files -g AGENTS.md …'    （61 行輸出）
```

點那一行就展開，再點就收回。`檢視` 選單可改成「完整顯示」或「完全隱藏」，選擇會記在工作區裡。

輸出其實**有**插進 widget，只是用 Tk tag 的 `elide` 屬性隱藏，所以：

- 展開／收合是瞬間的，**不會**重建逐字稿、也不會跳動捲軸位置
- `Ctrl+A` 全選複製時，被收合的輸出**照樣會被複製**（要的是完整記錄）

「完全隱藏」只是不畫出來，紀錄仍然存在 `workspace.json` 裡，改回「完整顯示」就看得到。

## 圖片

Codex CLI 的 `-i/--image` 可以附加圖片，而 GUI 讓這件事比終端機容易得多：

- **輸入框右鍵** — 選單會跟著剪貼簿內容變：有截圖時是「貼上圖片」，有複製的圖檔時是「貼上圖片（N 個檔案）」，都沒有時就是普通的「貼上」。
- **`Ctrl+V`** — 同樣的判斷邏輯；沒有圖片時照原本貼上文字。
- **「附加圖片」鈕** — 用檔案對話框選，可多選。
- 附件在輸入框上方顯示成**縮圖卡片**，每張都能單獨 ✕ 移除；檔名過長會省略。附件跟著各自的對話走，不會跑到別的對話。
- 只附圖不打字也能送。
- 送出後，**逐字稿裡會留下可點的縮圖**（連檔名也可點），點下去用系統預設程式開啟原圖。圖檔留在 `attachments` 資料夾，所以回頭翻舊對話也還看得到。Tk 解不開的格式（JPEG、WEBP）沒有縮圖，但檔名一樣可點。

實作上有兩個坑值得記：

1. **`-i` 在 `exec` 上是變長參數**（`<FILE>...`），所以 `-i a.png "你的問題"` 會把問題也吃成圖檔，最後因為沒有 prompt 而去讀 stdin。必須**每個檔案重複一次 `-i`**。
2. **剪貼簿貼圖沒有用第三方套件。** Tkinter 讀不到剪貼簿的圖片格式，而這個專案不想引入 Pillow，所以用 ctypes 直接讀 Win32 剪貼簿的 DIB，再轉成 PNG（純標準庫，`zlib` 就夠）。
   宣告 ctypes 的 `restype` 不是可選的：`GetClipboardData` 與 `GlobalLock` 回傳的是 handle 與指標，ctypes 預設 `c_int` 會在 64 位元 Python 上**默默把它們截斷成 32 位元**，handle 看起來有效但指向錯誤位置。
3. **為什麼是 PNG 而不是 BMP。** `-i` 兩種都接受，但 Tk 的 `PhotoImage` 只解得開 PNG 與 GIF — 存成 BMP 就永遠做不出縮圖預覽。PNG 也小得多：同一張 200×80 的截圖，PNG 301 bytes，BMP 約 28 KB。
   DIB 轉 PNG 有三個容易錯的地方：**列順序**（`biHeight` 為正代表由下往上，負值才是由上往下）、**BGR 而非 RGB**、以及 **alpha 要丟掉**（`Clipboard.SetImage` 常給出 alpha 全 0 的 32bpp 像素，照用會得到全透明的圖）。解不開的像素格式（16bpp、RLE 等）會退回 BMP。

貼上的圖存在 `%USERPROFILE%\.tree_agent\attachments\`。

## 程式碼審查

專案右鍵「審查未提交的變更」會在該專案下開一個新對話，跑 `codex exec review --uncommitted`。

一個 CLI 的限制：`--uncommitted` **不能同時帶 prompt**（`the argument '--uncommitted' cannot be used with '[PROMPT]'`），所以這個動作不接受自訂指示。

## 用量統計

每回合結束時 `turn.completed` 會回報 token 用量，這些會累計下來：

- **對話標題列**顯示該對話的累計（回數、input、cached、output）
- **專案頁**顯示整棵子樹的加總

## 對話自動命名

送出第一則訊息時，對話會從那則訊息取一個標題。**在本機算出來的，不會另外問 Codex** —— 那要多花一整回合和一份 token，而開場訊息本身就是最好的摘要。

截斷規則是照實際資料訂的。這裡的第一則訊息常長這樣：

```
"F:\eic_server\eic_server_std_dev\kws\home_new.aspx" 有什麼作用
```

直接從前面截斷會得到 `"F:\eic_server\eic_serv` —— 保留了磁碟機、丟掉了真正的問題。所以會**先把看起來像路徑的 token 縮成檔名**，再截斷：

| 第一則訊息 | 標題 |
| --- | --- |
| `"F:\kws\home_new.aspx" 有什麼作用` | `home_new.aspx 有什麼作用` |
| `scan project` | `scan project` |
| `implement  3d shot game` | `implement 3d shot game`（空白收斂） |
| 只附圖沒打字 | 圖檔的檔名 |

幾條規則：

- **只改暫名。** 只有 `新對話`／`新對話 2`／`新對話1` 這類佔位名稱會被取代；你自己取的名字、分岔的 `X (分岔)`、`程式碼審查` 都不動。
- **只在第一則訊息。** 之後的訊息不會再改標題。
- **內容太少就不改** —— 例如只回一個 `1`，保留暫名比取個沒用的標題好。
- 同層撞名會自動加序號。

## 專案提示詞

專案設定表單有一個「提示詞」欄位，可以寫給 Codex 的專案層指示。

**和其他設定不同，提示詞是「累加」而不是「覆蓋」。** 工作目錄／模型／沙箱是子專案覆寫上層；提示詞則是從最上層一路串到目前這層 —— 因為「客戶通則」加上「這個子系統的細節」比兩者互相取代有用：

```
客戶A          提示詞：一律用繁體中文回覆。
  認證中心      提示詞：這個子系統用 OAuth2，注意 redirect_uri。
    登入頁      （沒寫）
      💬 排查 401  → 實際送出：上面兩段，由上而下串接
```

### 怎麼交給 Codex

Codex **沒有** `--instructions` 這種旗標；它原生的專案指示機制是工作目錄裡的 `AGENTS.md`。我沒有走那條路 —— 那等於去改你的 repo，而且會連帶影響你從別處使用 Codex。

改成：**只在新 thread 的第一則訊息**把提示詞接在你的問題前面（中間用 `---` 分隔）。之後 thread 自己記著，不必重送：

- 第一回合送出 → `提示詞

---

你的問題`
- 之後每一回合 → 只送你的問題（`resume` 已經帶著上下文）
- 分岔出來的對話 → 也不重送（它繼承來源 thread 的上下文）

逐字稿裡會留一行「已套用「路徑」的專案提示詞（N 字）」，所以這不是看不見的魔法；右側資訊面板也會顯示目前生效的完整內容。存下來的訊息只有你打的字，不含前綴。

一個限制要講清楚：**提示詞改了不會影響已經開始的對話**，因為指示已經在那個 thread 的上下文裡了。要讓新指示生效就「重設對話」或開新對話。

## 權限

沙箱模式決定 Codex 能做多少事，設在專案上、由子專案與對話繼承。**預設是 `no-sandbox`**，也就是最高權限 — 因為 Codex 自己的預設 `workspace-write` 在網路磁碟上根本跑不動（見下一節），而這個工具指向的儲存庫就放在網路磁碟上。任何專案都能自己覆寫。

| 模式 | 能做什麼 |
| --- | --- |
| `read-only` | 只能讀檔 |
| `workspace-write` | 可寫入工作目錄（外加系統暫存目錄） |
| `danger-full-access` | **最高權限** — 讀寫與網路都不受限，不限於工作目錄 |
| `no-sandbox` | 最高權限，並額外跳過核准機制（對應 `--dangerously-bypass-approvals-and-sandbox`） |

要注意 Codex **沒有**「只在工作目錄內有最高權限」這種模式：`workspace-write` 是把寫入限制在工作目錄，而 `danger-full-access` 是整台機器都不設限。網路磁碟上的專案只能用後兩者（原因見下）。

沙箱權限和 `AGENTS.md` 是**兩道獨立的閘門**。如果 `~/.codex/AGENTS.md` 要求 Codex 動作前先確認（例如「任務執行前確認規則」這類），那即使沙箱給了最高權限，第一回合仍然只會回你一份確認清單而不動手 — 那是提示詞層面的限制，不是權限問題。

## 網路磁碟（`CreateProcessWithLogonW failed: 267`）

如果工作目錄放在對應的網路磁碟（`F:`、`G:` 這類指向 `\\server\share` 的磁碟機），Codex 的每一個指令都會失敗：

```
execution error: Io(Custom { kind: Other,
  error: "windows sandbox: CreateProcessWithLogonW failed: 267" })
```

原因是 Codex 的 Windows 沙箱會用 `CreateProcessWithLogonW` **以另一個受限使用者的身分**執行指令，而**磁碟機對應屬於登入工作階段（logon session）**。那個沙箱使用者的工作階段裡沒有 `F:` 這個對應，所以 `F:\...` 對它是無效目錄 → `ERROR_DIRECTORY (267)`。

實測（codex 0.147 與 0.149 皆相同）：

| 工作目錄 | 沙箱模式 | 結果 |
| --- | --- | --- |
| `E:\...`（本機磁碟） | `read-only` | ✅ |
| `F:\...`（網路磁碟） | `read-only` | ❌ 267 |
| `F:\...`（網路磁碟） | `workspace-write` | ❌ 267 |
| `F:\...`（網路磁碟） | `danger-full-access` | ✅ 可讀可寫 |
| `F:\...`（網路磁碟） | `no-sandbox` | ✅ |

只有 `read-only` 與 `workspace-write` 會建立受限使用者沙箱，所以只有這兩個會壞。`danger-full-access` 根本不建沙箱，因此完全不受影響。

**這不是 Tree Agent 造成的** — 直接用 `codex exec` 在同一個目錄跑會得到一模一樣的錯誤。

解法：把該專案的沙箱模式改成 `danger-full-access`，或把專案複製到本機磁碟再跑。

Tree Agent 會**在你按下送出之前**就偵測到這個組合，在對話標題下方與專案設定頁顯示警告，不用等 Codex 跑完才發現。

## 匯出與匯入

右鍵選單會依你點的地方給不同選項；`檔案` 選單裡也有同一組：

| 你點的地方 | 提供的動作 |
| --- | --- |
| 專案 | 匯出這個專案… / 匯出為 Markdown… / 匯入到這個專案… |
| 對話 | 匯出這個對話… / 匯出為 Markdown… |
| 樹的空白處 | 匯出整個工作區… / 匯入到最上層… |

四種動作的產出：

| 動作 | 產出 | 能匯回來嗎 |
| --- | --- | --- |
| 匯出選取的專案／對話… | `.zip` | ✅ |
| 匯出整個工作區… | `.zip` | ✅ |
| 匯出為 Markdown… | `.md` | ❌ 單向，給人讀的 |
| 匯入… | — | 接受上面兩種 `.zip`，也接受單獨的 manifest `.json` |

**為什麼是 zip 而不是單一 JSON。** 附件圖檔存在 `attachments` 資料夾，不在 `workspace.json` 裡；只匯出 JSON 會把圖弄掉。所以 zip 裡放一份 manifest 加上被引用到的圖檔，匯入時解到目的工作區並把路徑改寫過去。

匯入的行為：

- **只新增，不覆蓋。** 節點 id 一律重新產生，所以同一個檔匯入兩次會得到兩份獨立副本，不會撞號。名稱撞到會自動加序號（`客戶A 2`）。
- **匯到哪裡**：目前選取的專案底下；沒有選取就放最上層。單獨匯入一個對話時，因為對話不能放在最上層，會自動包一個「匯入的對話」專案。
- **附件不會互相覆蓋** — 同名檔案會加序號。
- **`thread_id` 會一起帶走，但它只在原本那台電腦有效**（Codex 的 session 存在該機的 `~/.codex/sessions`）。所以從別台機器匯入的對話，逐字稿讀得到，但要接著問下去得先「重設對話」開新 thread。匯入時如果偵測到來源電腦不同且有帶 thread，會明白告訴你這件事。
- 匯出檔的 `format` / `version` 會驗證；不是 Tree Agent 的檔案、或版本比程式新，都會直接拒絕而不是硬吃。

## 資料存放

全部集中在 `%USERPROFILE%\.tree_agent\workspace.json` — 專案樹、每則訊息、每個對話的 Codex `thread_id`、視窗大小與上次選取的節點。

寫入採「先寫暫存檔再改名」，所以中途斷電不會弄壞工作區；讀取時若檔案損毀，會改名成 `.corrupt` 保留，不會直接丟掉。串流中的訊息寫入會合併（約每 0.5 秒一次），避免一次 turn 產生大量小寫入。

同一個工作區資料夾同時只能開一個視窗。開啟時會在 `.lock` 上取得一個位元組範圍鎖（行程結束時由作業系統自動釋放，不會留下需要手動清掉的殘留鎖檔）；第二個視窗會提示已被哪個 PID 佔用，並建議改用 `--home` 開另一個工作區。不同 `--home` 之間互不影響。

Codex 自己的 session 檔案仍然放在 `~/.codex/sessions`，Tree Agent 只保存 `thread_id` 並透過 `codex exec resume` 接續，沒有另外複製一份對話。

### 怎麼呼叫 Codex

一次 turn = 一個 `codex exec` 行程。

```
# 第一次（建立新 thread）
codex exec --json --skip-git-repo-check -s <sandbox> [-m <model>] -

# 之後每一次（接續同一個 thread）
codex exec --json --skip-git-repo-check -s <sandbox> [-m <model>] resume <thread_id> -
```

三個關鍵細節：

1. **prompt 走 stdin**（最後那個 `-`）。Windows 上 `codex` 是 `codex.CMD`，如果把 prompt 當命令列參數傳，引號、換行、`&`、`|` 都會被 cmd.exe 解析掉。走 stdin 完全繞過這個問題。
2. **共用選項必須寫在 `resume` 之前**。`codex exec resume -s read-only ...` 會直接報 `unexpected argument '-s'`。
3. **子行程用 `CREATE_NO_WINDOW` 建立**，否則每次送出都會閃一個黑色主控台。

`thread_id` 從 `--json` 輸出的第一個事件取得：

```json
{"type":"thread.started","thread_id":"01a0236d-674c-7351-9de9-f2d71d0bf93f"}
{"type":"turn.started"}
{"type":"item.completed","item":{"type":"agent_message","text":"…"}}
{"type":"turn.completed","usage":{"input_tokens":19979,"output_tokens":18}}
```

`item.completed` 會依 `item.type` 分別呈現成回覆、思考、指令執行、檔案變更、待辦清單、MCP 呼叫等；未知的 type 也會照實顯示而不是吞掉，這樣 Codex 之後新增事件類型時不會靜默漏掉內容。

Codex 的回覆是 Markdown，會渲染成標題、粗體/斜體、行內 code、程式碼區塊、清單、引言、表格與連結。只有 agent 的回覆會渲染 — 你自己輸入的文字、指令輸出與錯誤訊息都照原樣顯示，避免把不是 Markdown 的內容誤改樣子。`redirect_uri` 這種底線命名不會被誤判成斜體。

子行程的環境變數會加上 `NO_COLOR=1`。Codex 會把它傳給它啟動的 shell，PowerShell 就不會給表頭上色 — 否則擷取到的輸出會夾帶 `[32;1m` 這類控制碼，在畫面上變成亂碼，也白白佔用 Codex 自己的 context。顯示時另外再清一次，讓在這個修正之前就存下的逐字稿也能正常呈現。

停止執行時用 `taskkill /F /T /PID` 而非 `terminate()` — `codex.CMD` 只是個 shim，真正的 agent 是它底下的 node 行程，`terminate()` 只會收掉 shim。

- `test_panels` — 兩側面板：面板寬度固定且逐字稿仍受寬限、大綱項目／層級／順序正確且多行提問只取首行、點大綱會捲到該處、資訊面板列出設定與用量與變更檔案、視窗變窄時先收資訊面板再收大綱、偏好可關閉並跨重啟保存、空對話顯示佔位文字。**離線執行。**
